# 数据一致性、安全与演进设计

## 一、设计目标

本方案关注正常业务之外的四类系统性问题：

1. 多条记录如何整体变更。
2. 跨身份服务、数据库和对象存储时如何处理部分失败。
3. 浏览器、应用服务和数据层之间如何划分安全边界。
4. 新模块和未来能力如何在不破坏现有语义的情况下演进。

各模块落地时共同遵循的字段、分页、错误、幂等和权限约定见 [模块数据库与接口设计](modules/README.md)。

## 二、事实源与数据所有权

每类信息只能有一个权威事实源：

| 信息 | 权威事实源 | 可存在的派生信息 |
| --- | --- | --- |
| 密码与会话 | 身份服务 | 浏览器会话副本 |
| 业务用户状态 | 业务用户数据 | 会话中的短期上下文 |
| 用户最终权限 | 角色与权限关系 | 界面权限集合 |
| 菜单层级与排序 | 菜单配置 | 前端渲染树 |
| 部门关系 | 部门树与用户部门引用 | 部门名称、人数快照 |
| 文件对象 | 私有对象存储 | 文件元数据与校验和 |
| 文件业务归属 | 文件绑定关系 | 页面中的附件列表 |
| 操作证据 | 不可变审计记录 | 查询索引与展示摘要 |

派生信息可以提升读取效率，但必须能够从权威数据重建，并在权威关系变化时同步或失效。

## 三、数据库内一致性

### 3.1 唯一性

账号、角色编码、权限编码、有效部门编码和有效菜单路径等稳定标识必须唯一。大小写和前后空格的规范化在写入前统一完成，避免视觉上相同但实际不同的标识。

### 3.2 引用完整性

关系只能指向有效对象。软删除不会自动让外部引用变得合理，因此删除前需要检查有效引用，删除后清理只服务于已经确认不再使用的关系。

系统需要重点保护：

- 用户与角色、角色与权限的关系；
- 用户与部门、部门与负责人、部门与父级的关系；
- 菜单与父级、菜单与显示权限的关系；
- 文件与业务资源的绑定关系。

### 3.3 树结构

部门树和菜单树都必须阻止自引用、无效父级和任意深度循环。只在页面上限制拖拽不能保证数据安全，数据层必须具备最终环检测。

### 3.4 软删除

软删除用于保留历史语义，但不等于可以忽略引用。删除策略遵循：

1. 系统保护对象拒绝删除。
2. 存在有效业务引用时拒绝删除，并指出需先处理的关系。
3. 成功软删除后，清理不再有意义的纯授权关系。
4. 所有常规查询默认排除软删除对象。

## 四、原子变更

以下操作必须以最终集合或整批数据为单位提交：

- 用户角色替换；
- 角色权限替换；
- 部门批量导入；
- 其他需要先删除旧关系再写入新关系的配置。

原子变更统一采用“先完整校验、再同一事务写入”的策略。任何目标或引用无效时，旧状态保持不变；不能先清空旧关系，再逐条尝试写入。

整体替换还需要处理并发：客户端应基于最新版本提交，服务端可使用更新时间或版本号检测丢失更新。若两个管理员同时编辑同一角色，后提交者不应在无提示的情况下覆盖前者结果。

## 五、跨系统一致性

身份服务、业务数据库和对象存储无法共享数据库事务，因此采用 Saga 式的顺序与补偿设计。

### 5.1 设计模板

每个跨系统流程都要明确：

- 起始状态；
- 主操作顺序；
- 每一步的幂等键；
- 失败时的反向补偿；
- 补偿失败后的可识别状态；
- 人工或后台修复入口；
- 审计和关联标识。

### 5.2 身份开通

先确认业务用户符合开通条件，再创建认证身份并绑定。绑定确认失败时回收新身份。重复请求必须识别“已完成”和“冲突身份”，不能创建多个身份。

### 5.3 用户创建与授权

如果业务用户和角色关系需要同时创建，应在一个数据库事务中完成；无法共用事务时，角色分配失败就删除尚未对外可见的新用户。已经被其他业务引用的用户不能再作为补偿对象直接删除。

### 5.4 文件上传

先写私有对象，再写元数据；元数据失败时删除对象。对象删除补偿失败时记录孤儿对象标识，进入后台对账队列。

### 5.5 文件删除

删除需要兼顾“对象不可继续访问”和“元数据可解释”。建议引入删除中状态：先阻止新下载，再删除对象和绑定，最后完成软删除。任何中断都可以根据状态重试，而不是让元数据仍显示就绪但对象已经不存在。

## 六、权限安全边界

### 6.1 浏览器

浏览器只持有可公开配置和用户会话，不持有数据库高权限凭据。按钮和菜单显隐属于体验优化，任何客户端提交内容都不作为权限事实。

### 6.2 应用服务

应用服务是唯一业务入口，负责：

- 校验会话和用户状态；
- 计算动作权限；
- 执行目标资源保护；
- 限制可写字段和批量规模；
- 生成对象路径、操作者和审计上下文；
- 把底层错误转换为稳定业务语义。

服务端拥有高权限凭据并不意味着可以信任所有内部调用。模块之间仍应通过清晰的业务边界和最小数据访问工作。

### 6.3 数据层

业务表默认不允许浏览器身份直接访问。数据层用唯一约束、引用约束、格式约束、树环校验、系统对象保护和原子事务兜底。

新增数据对象时，必须同时设计访问策略和最小授权；“先建表、以后再补权限”会形成默认暴露窗口。

### 6.4 对象存储

文件空间默认私有，上传位置由服务端决定，下载使用短时签名。文件类型、大小、状态和绑定关系由业务层控制，签名地址本身也视为敏感信息。

## 七、输入、输出与错误

### 7.1 输入边界

- 只接受明确声明的字段，未知字段拒绝。
- 标识、分页、排序、日期、文件大小和批量条数都有上限。
- 排序字段采用白名单，不能把客户端文本直接用于数据查询结构。
- 批量导入先解析为规范化模型，再进入业务校验。

### 7.2 错误语义

错误至少区分：未认证、权限不足、目标受保护、资源不存在、唯一冲突、引用无效、数据格式错误、外部依赖失败和内部失败。

对外返回稳定错误标识和可行动文案；数据库原始消息、堆栈、凭据和内部路径只留在受控日志。相同业务原因在不同模块中应使用一致语义，便于前端、本地化和监控聚合。

## 八、审计与可观测性

所有跨系统和高风险操作使用统一请求关联标识贯穿业务结果、审计记录和服务日志。至少应监控：

- 认证失败与被禁用用户访问；
- 权限拒绝和角色分配防提升命中；
- 审计写入失败；
- 数据库约束冲突；
- 身份创建补偿失败；
- 文件对象与元数据补偿失败；
- 批量导入失败率和错误行分布。

日志用于诊断，审计用于证据，两者可以共享关联标识，但不能相互替代。

## 九、备份与恢复

恢复方案需要覆盖三个彼此关联的部分：业务数据库、身份关联和文件对象。

- 只恢复数据库而不恢复文件会产生失效附件。
- 只恢复对象而不恢复元数据会产生孤儿文件。
- 身份恢复后必须核对与业务用户的一对一绑定。
- 角色、权限和菜单初始化数据可以重建参考配置，但不能替代业务数据备份。
- 审计数据应按证据保留要求制定独立周期，不能混入普通软删除清理。

恢复演练至少验证用户能登录、权限可解释、菜单可生成、文件可下载、审计可查询以及部门树无断链。

## 十、演进策略

### 10.1 新增业务模块

每个模块按顺序设计：领域对象和状态、稳定标识、引用与删除规则、权限矩阵、失败边界、审计事件、导航入口、数据迁移和验收场景。

### 10.2 多租户

多租户不是给用户增加一个租户字段就完成。租户维度需要同时进入用户授权、角色作用域、业务数据唯一性、查询边界、审计和文件对象路径。跨租户角色与共享资源需要单独规则。

### 10.3 数据范围权限

动作权限回答“能做什么”，数据范围回答“能对哪些数据做”。未来可增加本人、本部门、部门树或自定义范围策略，但应在动作授权之后独立计算，不能把范围编码进菜单或复制大量角色。

### 10.4 缓存

权限、菜单和组织树只有在明确失效机制后才能缓存。角色、权限、用户状态或菜单变化必须能主动失效相关用户缓存；否则宁可保持实时计算，也不要接受难以解释的旧授权。

## 十一、验收标准

- 核心稳定标识唯一且规范化，树结构无法形成循环。
- 有效引用对象不会被普通删除破坏。
- 集合替换与批量导入失败时保持原状态。
- 并发编辑不会无提示覆盖他人刚提交的配置。
- 身份和文件跨系统操作具备幂等、补偿、告警和人工修复路径。
- 浏览器无法持有高权限凭据或直接绕过应用层访问业务数据。
- 敏感输入不会进入普通响应、审计正文或非受控日志。
- 关键写操作可以用同一关联标识串联业务结果、审计和日志。
- 备份恢复能够同时还原用户授权、组织关系、文件元数据与对象。
- 新模块在上线前具备权限矩阵、失败场景和数据迁移验收。
