# RBAC 与菜单设计

## 一、设计目标

权限方案需要做到：

1. 授权结果简单、稳定、可解释。
2. 页面可见性、按钮可见性和服务端动作授权使用同一套权限语言。
3. 多角色合并不产生优先级冲突。
4. 管理员不能通过角色转授扩大自身权限。
5. 菜单可以灵活配置，但不能成为安全边界。

模块级表结构与接口契约分别见 [RBAC 模块](modules/rbac.md) 和 [菜单模块](modules/menus.md)。

## 二、权限模型

### 2.1 四个核心对象

| 对象 | 含义 |
| --- | --- |
| 用户 | 授权主体，可同时拥有多个角色 |
| 角色 | 一组可复用的权限集合 |
| 权限 | 对某类资源执行某个动作的能力 |
| 授权关系 | 用户到角色、角色到权限的多对多关系 |

权限采用“资源.动作”的稳定编码方式。资源表达操作对象，动作表达能力，例如查看、创建、更新、删除、分配角色、管理登录身份、上传或导入。

通用查看和高风险操作必须拆开。能查看用户不应自动获得分配角色或重置密码的能力；能查看文件也不应自动获得上传、下载和删除能力。

### 2.2 Grant-only 模型

存在角色权限关系表示允许，不存在表示未授权，不设置显式拒绝。用户拥有多个角色时，最终权限为所有启用角色中启用权限的并集。

选择这一模型的原因：

- 任意权限都能追溯到至少一个角色；
- 不需要定义允许与拒绝的优先级；
- 角色组合不会因顺序不同而得到不同结果；
- 权限计算和排障都更直观。

如果未来确实需要显式拒绝，应作为新的策略模型设计，不能直接在现有关系上增加一个布尔字段。

## 三、角色与权限生命周期

角色和权限都包含启用状态、系统保护标记和软删除状态。

- 禁用表示暂时不参与权限计算，但保留配置和历史关系。
- 软删除表示退出有效目录，不能再建立新关系。
- 系统角色和系统权限用于保证平台基础能力，普通管理操作不能修改或删除。
- 新建角色默认是普通角色，不能由客户端把自己标记为系统角色。

稳定编码用于关系、规则和迁移；展示名称和描述可以本地化或调整。编码一旦投入使用，应通过显式迁移变更，而不是在日常编辑中随意改名。

## 四、权限计算

权限计算遵循固定顺序：

1. 读取用户持有的角色。
2. 排除禁用或已删除角色。
3. 汇总角色关联权限。
4. 排除禁用或已删除权限。
5. 去重得到最终权限集合。

权限结果不能长期固化在用户档案中，否则角色或权限变化后会产生双重事实源。会话可以携带权限快照供界面快速判断，但服务端授权必须确保使用足够新的结果。

## 五、动作授权与资源保护

服务端授权分为两层：

### 5.1 动作级授权

判断操作者是否具备执行某类动作的权限，例如是否可以更新用户或管理角色权限。所有受保护业务动作都必须显式声明所需权限，不能依赖“进入了某个页面”推断。

### 5.2 资源级保护

具备动作权限后，还要判断是否允许操作这个具体目标：

- 不能删除自己；
- 非系统身份不能修改持有系统角色的用户；
- 系统角色和系统权限不可被普通变更；
- 不能修改自己当前持有角色的权限，以免操作过程改变自身授权基础；
- 不能删除仍被有效对象引用的角色或权限。

动作级授权解决“能不能做这类事”，资源级保护解决“能不能对这个对象做”。两者缺一不可。

## 六、角色分配防越权

给用户分配角色是高风险动作，需同时满足：

1. 操作者具备独立的角色分配权限。
2. 目标角色有效且可分配。
3. 如果目标角色是系统角色，操作者自己也必须持有系统角色。
4. 目标角色的有效权限集合必须是操作者自身权限集合的子集。
5. 目标用户若受系统身份保护，操作者也必须满足对应保护等级。

第四条用于阻止间接权限提升。例如操作者虽然可以编辑用户，但不能把自己没有的“删除角色”权限通过另一个角色授予他人。

用户角色关系使用“整体期望集合”更新，而不是多个独立增删请求。这样可以在一个一致性边界内校验最终结果，并避免并发请求造成丢失更新或短暂混合状态。

## 七、角色权限配置

角色权限同样采用整体替换语义：提交该角色最终应该拥有的完整权限集合，先验证全部权限有效，再一次性替换。

系统角色权限不可通过日常管理修改；操作者当前持有的角色也不允许由自己修改。需要调整基础系统角色时，应通过受控变更和独立复核完成。

权限目录本身更接近平台能力清单，通常随业务能力设计和版本变更维护，而不是允许任意管理员自由创建不受系统识别的权限码。

## 八、菜单模型

菜单是树形导航配置，包含稳定编码、父级、路径、页面标识、显示权限、状态、可见性、排序和多语言键。

菜单分为两类：

- 目录菜单：负责组织导航层级，可以不直接绑定权限。
- 页面菜单：指向一个可渲染页面，并绑定进入该页面所需的读取权限。

页面标识是菜单配置与前端页面注册之间的契约。数据库可以决定是否展示和如何排序，但不能凭空生成尚未注册的页面能力。

## 九、菜单可见性

菜单计算按以下规则进行：

1. 只考虑启用、可见、未删除菜单。
2. 选择显示权限命中用户权限集合的页面菜单。
3. 沿父级向上补齐全部目录，确保叶子入口有完整路径。
4. 移除没有任何可见后代的空目录。
5. 按稳定排序生成导航树。

菜单只决定导航入口是否出现：

- 隐藏菜单不能让服务端放松权限判断；
- 菜单可见也不自动授予页面内的创建、修改、删除等动作；
- 前端按钮显隐可以改善体验，但直接构造请求仍必须被服务端校验。

## 十、菜单维护约束

- 菜单路径在有效范围内唯一。
- 父菜单必须有效，不能自引用或形成循环。
- 页面菜单的显示权限应从页面标识对应的读取权限推导，避免手工绑定错误资源。
- 删除父菜单前必须处理有效子菜单。
- 展示名称变化时，应同步检查多语言键，防止名称与翻译语义错位。
- 新增页面菜单时，权限目录、页面注册、导航配置和多语言文案必须同时就绪。

## 十一、典型决策示例

| 需求 | 设计选择 | 原因 |
| --- | --- | --- |
| 一个用户兼任多个职责 | 多角色并集 | 避免复制“组合角色” |
| 临时停用角色 | 禁用角色 | 保留配置，立即退出计算 |
| 只隐藏页面入口 | 调整菜单可见性 | 不改变服务端授权 |
| 禁止某角色中的一个权限 | 从该角色移除授权 | 保持 grant-only 语义 |
| 给普通管理员授予高权限角色 | 拒绝 | 目标权限超出操作者自身范围 |
| 修改系统角色 | 走受控版本变更 | 避免运行时破坏平台基础能力 |

## 十二、验收标准

- 多角色权限结果等于各启用角色权限的去重并集。
- 禁用或删除角色、权限后不再参与授权。
- 普通管理员不能授予自己没有的权限，也不能授予系统角色。
- 直接访问隐藏菜单对应业务能力时，服务端仍独立判断权限。
- 有叶子权限时父目录自动可见，没有可见叶子时空目录不展示。
- 角色和权限被有效对象引用时不能被破坏性删除。
- 用户角色和角色权限替换要么全部生效，要么保持原状。
- 任意授权结果都可以追溯到用户角色和角色权限关系。
