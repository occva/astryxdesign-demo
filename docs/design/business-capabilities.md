# 业务能力设计

## 一、设计范围

本文描述用户与权限核心之外的后台能力：组织架构、仪表盘、通知、审计和文件。各模块共享统一身份、权限、软删除、错误和审计规则，但保持自己的数据所有权和业务边界。

模块接入时必须回答：管理什么对象、谁可以执行什么动作、数据如何失效、失败如何恢复、是否需要留下审计证据。

## 二、组织架构

### 2.1 目标

组织架构以部门树为唯一事实源，同时支持日常维护、树形浏览、成员统计和批量导入导出。不复制另一套“组织树”供不同页面使用。

### 2.2 部门模型

部门包含稳定编码、名称、父部门、负责人、状态、排序和描述。用户通过部门关系成为成员，负责人也是有效业务用户的引用。

稳定编码用于批量同步和跨环境识别；名称用于展示。父部门名称、负责人名称和成员数量可以作为查询优化信息，但权威关系仍是稳定标识。

### 2.3 树结构约束

- 部门不能以自己为父级。
- 父部门必须有效。
- 任意层级不能形成循环。
- 有有效子部门或成员的部门不能直接删除。
- 负责人必须是有效用户；用户仍负责部门时不能直接删除。
- 状态禁用不等于删除，禁用部门仍保留树关系和历史归属。

### 2.4 树形展示

组织架构页面同时呈现部门层级、直属成员和包含子树的汇总人数。直属人数与汇总人数必须区分，避免把下级成员重复算入当前部门直属成员。

桌面端适合采用树与详情并列，窄屏按“树选择—部门详情—成员列表”顺序堆叠。选择部门后，只更新详情区域，保持树展开上下文。

### 2.5 批量导入导出

导入使用稳定列：部门编码、名称、父部门编码、负责人账号、状态、排序和描述。以部门编码识别新增或更新对象。

导入分为两个阶段：

1. 预检：解析格式、规范化标识，检查必填、重复编码、父级存在、负责人存在、状态范围和完整树环。
2. 提交：再次执行同等校验，在单个一致性边界内写入主体、解析父级和负责人；任一记录失败则整批不生效。

预检返回总数、新增数、更新数以及精确到行和字段的错误。只有无错误时才允许提交。导出的文件应可以不修改直接重新导入，保证往返兼容。

## 三、仪表盘

### 3.1 目标

仪表盘提供面向当前用户的业务概览，而不是成为第二套数据存储。指标、趋势、模块占比和最近动态可以独立配置或聚合，但应在一次读取中形成一致的页面快照。

### 3.2 数据组织

仪表盘按展示用途划分为：

- 指标：值、变化量和趋势语义；
- 趋势：时间或类别序列与可选目标值；
- 模块占比：当前值、容量和颜色语义；
- 动态：事件标题、说明、时间和状态。

每类数据支持启用状态、稳定排序和多语言键。展示颜色与状态属于表达信息，不承载权限或业务判断。

### 3.3 权限与失败

仪表盘只使用独立的查看权限。读取多个数据分区时，方案需明确是“任一区块失败则整体失败”还是“允许区块降级”；当前建议整体失败并提供统一重试，避免用户把缺失区块误解为真实零值。

未来若指标按角色或部门变化，应增加明确的数据范围策略，而不是在展示层过滤已返回的全量数据。

## 四、通知

### 4.1 模型

通知正文与用户已读状态分离：通知保存标题、说明、类型、发布时间、失效时间和启用状态；已读关系只保存某用户何时读过某条通知。

这一设计避免为每个用户复制整条通知，也允许通知内容更新时保持原已读关系。

### 4.2 可见性与时效

用户只看到启用且未过期的通知。通知类型用于信息、成功、警告和错误等表达语义，不代表权限等级。

标记单条已读和全部已读都应具备幂等性，重复操作不产生重复关系或错误。全部已读只覆盖当前仍有效的通知，过期或禁用通知无需补写关系。

### 4.3 扩展边界

当前通知面向全部用户。如果未来需要定向通知，应增加明确的受众模型，例如用户、角色、部门或规则受众；不能通过前端拿到全部通知后自行过滤敏感内容。

## 五、操作审计

### 5.1 目标

审计回答：谁在什么时间，通过什么入口，对什么资源执行了什么动作，结果如何，以及提交和返回了哪些非敏感摘要。

审计是证据能力，不是普通业务日志。记录一旦写入不可修改、不可删除，操作者名称和账号保存当时快照，避免用户后续改名导致历史语义变化。

### 5.2 审计范围

所有已鉴权的业务写操作默认纳入审计，包括创建、更新、删除、导入、上传、下载、标记已读、管理身份和分配权限。公开登录失败等安全事件可进入独立认证安全日志，避免混淆业务审计 actor。

审计内容包括：

- 操作者稳定标识及名称、账号快照；
- 动作和资源类型、可选资源标识；
- 请求入口、请求关联标识；
- 成功或失败状态及结果码；
- 脱敏后的请求、响应或错误摘要；
- 合法的网络地址和客户端信息。

### 5.3 脱敏与限幅

密码、令牌、密钥、认证头、Cookie、签名下载地址及相似敏感键必须递归脱敏。文件二进制只记录大小，不记录内容。超长字符串、超大数组、过深对象都要截断，避免审计成为敏感数据副本或存储攻击入口。

### 5.4 审计失败

审计写入失败不应把已经成功的业务操作伪装成失败，也不应自动重放业务操作。系统需要记录请求关联标识并触发告警，使运维可以识别审计缺口。

对于法律或合规要求“无审计即不允许业务成功”的场景，应把审计写入纳入同一事务或可靠消息方案；这属于更高可靠性等级，需要单独设计。

## 六、文件与附件

### 6.1 对象与元数据分离

文件二进制保存在私有对象存储，业务数据库保存权威元数据，包括原始名称、类型、大小、校验和、对象位置、上传者、状态和删除状态。

对象位置由服务端生成，不能由客户端提供。原始文件名只用于展示和下载名称，不能直接成为对象路径，以避免覆盖、路径穿越和特殊字符问题。

### 6.2 文件绑定

文件与业务资源通过独立绑定关系连接，绑定坐标由资源类型、资源标识、字段标识和排序组成。同一文件可以在受控情况下绑定多个业务字段，业务对象删除时需要根据生命周期策略解除绑定或保留历史附件。

绑定关系不验证具体资源内容时，至少要限制资源类型和字段标识格式；高安全模块还应校验目标资源存在且操作者能访问该资源。

### 6.3 上传

上传流程：

1. 校验文件存在、数量、大小及必要的类型限制。
2. 规范化展示文件名，生成不可预测的对象位置。
3. 计算校验和并写入私有对象存储。
4. 保存元数据。
5. 元数据失败时删除已上传对象。

文件状态应预留就绪、隔离和失败等语义，为未来病毒扫描和内容审核扩展。未通过检查的文件不能生成下载地址。

### 6.4 下载与删除

下载只返回短时有效的签名地址，不能返回服务端存储凭据或永久公网地址。下载本身属于敏感动作，需要独立权限并进入审计。

删除先确认文件有效及引用处理策略，再删除私有对象、清理绑定并软删除元数据。对象存储与数据库不共享事务，因此每一步都要幂等，并为中途失败保留可对账状态。

## 七、权限建议

| 模块 | 建议权限拆分 |
| --- | --- |
| 部门 | 查看、创建、更新、删除、导入 |
| 仪表盘 | 查看 |
| 通知 | 查看、更新已读状态 |
| 审计 | 查看 |
| 文件 | 查看、上传、下载、删除、绑定 |

权限按实际风险拆分，不把所有动作压缩成一个“管理”权限。是否允许导出、批量导入、下载和身份管理都应独立评估数据泄露与破坏风险。

## 八、验收标准

- 部门树在任意层级下都不能形成循环，引用对象删除前得到保护。
- 组织树的直属人数和汇总人数语义明确且计算一致。
- 部门导入可预检、定位逐行错误，并保证整批原子提交。
- 仪表盘所有区块使用一致的启用、排序和失败策略。
- 通知已读操作幂等，过期或禁用通知不会继续展示。
- 所有已鉴权写操作生成不可变、可关联且已脱敏的审计证据。
- 私有文件不能通过永久公网地址访问，对象位置不可由客户端控制。
- 上传元数据失败可以补偿对象，删除中断可以通过对账识别和修复。
- 每个模块只使用统一 RBAC，不创建模块私有的用户或角色字段。
