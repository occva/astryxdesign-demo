# RBAC 模块：数据库与接口设计

## 一、模块边界

RBAC 模块负责角色目录、权限目录、用户角色和角色权限关系。它提供动作级授权事实，不负责菜单树，也不直接表达部门等数据范围。

## 二、数据库设计

### 2.1 `roles`：角色

| 字段 | 类型 | 必填 | 设计说明 |
| --- | --- | --- | --- |
| `id` | UUID | 是 | 角色主键 |
| `name` | 文本 | 是 | 展示名称 |
| `code` | 文本 | 是 | 稳定角色编码 |
| `description` | 文本 | 否 | 角色用途说明 |
| `scope` | 文本 | 否 | 预留的范围说明；当前不参与授权 |
| `status` | 枚举 | 是 | `enabled` 或 `disabled` |
| `is_system` | 布尔 | 是 | 系统保护标记，默认为否 |
| `created_at` | 时间 | 是 | 创建时间 |
| `updated_at` | 时间 | 是 | 更新时间及并发版本依据 |
| `deleted_at` | 时间 | 否 | 软删除时间 |

约束：角色名称非空；编码规范化为小写，以字母开头，只含字母、数字、下划线和连字符；有效角色编码唯一。系统角色不能通过日常接口修改或删除。

### 2.2 `permissions`：权限

| 字段 | 类型 | 必填 | 设计说明 |
| --- | --- | --- | --- |
| `id` | UUID | 是 | 权限主键 |
| `code` | 文本 | 是 | `resource.action` 稳定编码 |
| `name` | 文本 | 是 | 展示名称 |
| `resource` | 文本 | 是 | 资源编码 |
| `action` | 文本 | 是 | 动作编码 |
| `description` | 文本 | 否 | 权限风险和用途说明 |
| `status` | 枚举 | 是 | `enabled` 或 `disabled` |
| `is_system` | 布尔 | 是 | 系统保护标记 |
| `created_at` | 时间 | 是 | 创建时间 |
| `updated_at` | 时间 | 是 | 更新时间 |
| `deleted_at` | 时间 | 否 | 软删除时间 |

约束：权限编码全局唯一，资源和动作均使用小写下划线格式，编码必须与资源、动作一致。系统权限不能通过日常接口删除。

### 2.3 `user_roles`：用户角色

| 字段 | 类型 | 必填 | 设计说明 |
| --- | --- | --- | --- |
| `user_id` | UUID | 是 | 有效业务用户 |
| `role_id` | UUID | 是 | 有效角色 |
| `created_at` | 时间 | 是 | 分配时间 |
| `created_by` | UUID | 建议 | 分配操作者，便于解释来源 |

用户与角色组成复合主键。为按角色反查用户建立索引。关系只能指向未删除角色；新分配只允许启用角色。

### 2.4 `role_permissions`：角色权限

| 字段 | 类型 | 必填 | 设计说明 |
| --- | --- | --- | --- |
| `role_id` | UUID | 是 | 有效角色 |
| `permission_id` | UUID | 是 | 有效权限 |
| `created_at` | 时间 | 是 | 授权时间 |
| `created_by` | UUID | 建议 | 授权操作者 |

角色与权限组成复合主键。为按权限反查角色建立索引。关系存在即授权，不设置允许/拒绝字段。

### 2.5 删除与状态规则

- 禁用角色或权限保留关系，但不参与权限计算。
- 角色仍被有效用户持有时不能软删除。
- 权限仍被角色或菜单引用时不能软删除。
- 成功软删除后可清理失去意义的授权关系。
- `is_system` 只允许受控数据变更维护，不能由普通创建或更新请求设置。

## 三、权限计算契约

最终权限等于用户所有启用、未删除角色关联的启用、未删除权限之并集。输出按权限编码去重和稳定排序。

授权上下文至少包含：完整角色标识集合、角色编码集合、是否持有系统角色、权限编码集合。单个“主角色”只可用于展示，不可用于最终授权。

## 四、角色接口设计

| 方法与路径 | 权限 | 请求/查询 | 响应 | 核心规则 |
| --- | --- | --- | --- | --- |
| `GET /api/roles` | `roles.read` | 名称、编码、状态、更新时间、分页排序 | 角色分页列表 | 返回授权权限数量和被分配用户数量 |
| `GET /api/roles/:id` | `roles.read` | 角色标识 | 角色详情 | 返回版本和关系摘要 |
| `POST /api/roles` | `roles.create` | 名称、编码、说明、状态 | 新角色 | 强制为非系统角色 |
| `PATCH /api/roles/:id` | `roles.update` | 可编辑字段、版本 | 更新后角色 | 系统角色拒绝；版本冲突拒绝 |
| `DELETE /api/roles/:id` | `roles.delete` | 角色标识、版本 | 无内容 | 系统角色或仍被用户持有时拒绝 |

角色列表和详情中的“权限数量”必须表达权限授权数量，不能使用菜单数量等历史兼容命名。

## 五、权限目录接口设计

权限目录主要随版本和业务模块演进，默认只开放读取：

| 方法与路径 | 权限 | 查询 | 响应 | 核心规则 |
| --- | --- | --- | --- | --- |
| `GET /api/permissions` | `permissions.read` 或 `role_permissions.read` | 资源、动作、状态、关键词 | 权限分组列表 | 默认只返回有效权限 |
| `GET /api/permissions/:id` | 同上 | 权限标识 | 权限详情及引用摘要 | 不暴露内部迁移信息 |

若确需运行时维护权限目录，应另设平台级权限，并限制编码变更和系统标记；普通角色管理员不应自由创建系统无法识别的权限。

## 六、角色权限接口设计

| 方法与路径 | 权限 | 请求 | 响应 | 核心规则 |
| --- | --- | --- | --- | --- |
| `GET /api/roles/:roleId/permissions` | `role_permissions.read` | 角色标识 | 全部有效权限及授权勾选态 | 便于配置完整集合 |
| `PUT /api/roles/:roleId/permissions` | `role_permissions.manage` | 完整权限标识集合、角色版本 | 最终授权集合与新版本 | 原子替换；系统角色和自身角色拒绝 |

替换前一次性校验权限标识不重复、全部有效，并校验操作者是否允许配置这些权限。除系统角色保护外，建议目标权限集合也不得超出操作者自身有效权限，保证角色维护和用户分配使用一致的防提升原则。

## 七、用户角色接口设计

用户角色接口归属用户资源，但使用 RBAC 规则：

| 方法与路径 | 权限 | 请求 | 响应 | 核心规则 |
| --- | --- | --- | --- | --- |
| `GET /api/users/:userId/roles` | `users.read` | 用户标识 | 当前角色集合和可分配提示 | 不返回不可见敏感配置 |
| `PUT /api/users/:userId/roles` | `users.assign_roles` | 完整角色集合、用户版本 | 最终角色集合 | 原子替换、防系统角色和权限提升 |

## 八、事务、并发与缓存

- 用户角色和角色权限整体替换各自使用单事务。
- 替换前验证全部引用，再删除旧集合并写入新集合。
- 更新请求携带资源版本，避免两名管理员相互覆盖。
- 角色、权限、关系或用户状态变化后，相关授权缓存必须失效。
- 如果无法保证主动失效，服务端授权使用实时关系计算。

## 九、主要错误

| 场景 | 建议错误码 |
| --- | --- |
| 系统角色禁止变更 | `SYSTEM_ROLE_PROTECTED` |
| 系统权限禁止变更 | `SYSTEM_PERMISSION_PROTECTED` |
| 修改自身当前角色权限 | `SELF_ROLE_PERMISSION_CHANGE_DENIED` |
| 角色仍被用户持有 | `ROLE_IN_USE` |
| 权限仍被角色或菜单引用 | `PERMISSION_IN_USE` |
| 角色不可分配 | `ASSIGNABLE_ROLE_NOT_FOUND` |
| 角色分配权限不足 | `ROLE_ASSIGNMENT_DENIED` |
| 系统角色分配被拒绝 | `SYSTEM_ROLE_ASSIGNMENT_DENIED` |
| 目标授权超出操作者权限 | `ROLE_PERMISSION_ESCALATION_DENIED` |
| 资源版本冲突 | `RESOURCE_VERSION_CONFLICT` |

## 十、验收标准

- 权限编码、资源和动作保持一致且唯一。
- 多角色结果是启用授权的去重并集，没有隐式拒绝或优先级。
- 系统角色和系统权限不能被日常接口破坏。
- 角色仍被使用、权限仍被引用时无法删除。
- 用户角色和角色权限替换在失败时保持原集合。
- 普通管理员不能配置或分配超出自身权限的角色。
- 并发编辑产生明确冲突，不静默覆盖。
