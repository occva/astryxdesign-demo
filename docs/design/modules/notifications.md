# 通知模块：数据库与接口设计

## 一、模块边界

通知模块负责发布时效信息和保存用户已读状态。当前设计面向全体用户；定向受众属于后续扩展，不允许由前端获取全量通知后自行过滤。

## 二、数据库设计

### 2.1 `notifications`：通知

| 字段 | 类型 | 必填 | 设计说明 |
| --- | --- | --- | --- |
| `id` | UUID | 是 | 通知主键 |
| `title` | 文本 | 是 | 标题 |
| `description` | 文本 | 是 | 正文摘要，可为空文本 |
| `status` | 枚举 | 是 | `info/success/warning/error` 展示语义 |
| `created_at` | 时间 | 是 | 发布时间 |
| `expires_at` | 时间 | 否 | 失效时间，空表示长期有效 |
| `active` | 布尔 | 是 | 发布开关 |
| `i18n_key` | 文本 | 否 | 多语言键 |

索引覆盖启用通知的发布时间倒序和失效时间。状态只表示视觉与信息语义，不表示访问等级。

### 2.2 `notification_reads`：用户已读

| 字段 | 类型 | 必填 | 设计说明 |
| --- | --- | --- | --- |
| `user_id` | UUID | 是 | 有效业务用户 |
| `notification_id` | UUID | 是 | 通知 |
| `read_at` | 时间 | 是 | 首次或最近读时间，需统一语义 |

用户和通知组成复合主键，保证标记已读幂等。为按通知反查建立索引。用户或通知物理清理时可以级联清理关系。

### 2.3 定向通知扩展

未来增加受众时，建议独立建立通知受众关系，支持用户、角色和部门等明确类型。用户可见性在服务端求并集并去重，已读表仍保持用户级关系。

## 三、用户接口设计

| 方法与路径 | 权限 | 请求/查询 | 响应 | 核心规则 |
| --- | --- | --- | --- | --- |
| `GET /api/notifications` | `notifications.read` | 可选已读状态、分页 | 当前用户有效通知 | 只返回启用、未过期且属于当前用户受众的数据 |
| `PUT /api/notifications/:id/read` | `notifications.update` | 通知标识 | 最终已读状态 | 重复标记幂等，不接受其他用户标识 |
| `PUT /api/notifications/read-all` | `notifications.update` | 可选筛选快照 | 更新数量和完成时间 | 只覆盖当前仍有效、可见通知 |

列表项包含标题、说明、信息状态、发布时间、已读状态和多语言键。未读数量可随列表返回或由独立轻量读取提供。

## 四、管理接口建议

若需要后台发布通知，应单独增加 `notifications.manage` 权限，并提供创建、修改、停用和预览能力。已发布通知的正文修改可能改变已读语义，建议重要修改创建新版本或重置已读关系，并在产品上明确提示。

## 五、一致性与并发

- 单条和全部已读使用 upsert 语义，重复调用结果一致。
- 全部已读按服务端执行时刻的有效通知集合处理；执行期间新发布通知保持未读。
- 通知过期或停用不需要删除已读历史。
- 标记不存在、已过期或不属于当前用户的通知时，不泄露其存在性。

## 六、主要错误

| 场景 | 建议错误码 |
| --- | --- |
| 通知不存在或不可见 | `NOTIFICATION_NOT_FOUND` |
| 通知已失效 | `NOTIFICATION_EXPIRED` |
| 发布内容无效 | `NOTIFICATION_INVALID` |
| 并发管理版本冲突 | `RESOURCE_VERSION_CONFLICT` |

## 七、验收标准

- 用户只能读取自己的可见通知，不能提交其他用户标识读取已读态。
- 过期、停用通知不展示，已有已读历史保持可解释。
- 单条和全部已读重复调用均幂等。
- 全部已读不会误标记操作完成后新发布的通知。
- 定向通知扩展后，受众过滤在服务端完成。
