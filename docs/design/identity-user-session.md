# 身份、用户与会话设计

## 一、设计目标

身份与用户设计需要解决四个问题：

1. 登录凭据与业务档案如何解耦。
2. 注册、管理员建档和登录开通如何共存。
3. 用户状态、角色变化如何及时影响会话。
4. 身份系统与业务数据之间失败时如何恢复。

核心选择是将“认证身份”和“业务用户”作为两个不同对象管理。认证身份只包含凭据与会话能力；业务用户保存账号、姓名、联系方式、组织关系、状态和授权关系。

本方案对应的表结构、字段约束和资源契约见 [身份与用户模块：数据库与接口设计](modules/identity-users.md)。

## 二、概念模型

### 2.1 认证身份

认证身份由身份服务管理，负责密码验证、令牌签发、令牌刷新和全局注销。业务系统不保存密码，也不自行复制一套令牌签发机制。

### 2.2 业务用户

业务用户是系统内的人员档案，至少包含：

- 稳定用户标识；
- 唯一业务账号；
- 姓名和业务联系方式；
- 正常或禁用状态；
- 所属部门和组织属性；
- 角色关系；
- 登录开通状态和最近登录时间；
- 软删除状态。

业务账号是人员在本系统中的稳定识别符。展示姓名、部门名称和联系方式可以变化，账号变化需要更严格的生命周期约束。

### 2.3 一对一关联

一个认证身份最多绑定一个有效业务用户，一个业务用户最多绑定一个认证身份。未绑定身份的业务用户可以参与组织管理、资源归属和负责人配置，但不能登录。

这一设计允许人事或管理员先完成建档，待需要访问系统时再开通登录，也避免为了保存业务档案而创建无密码或弱密码身份。

## 三、用户生命周期

业务用户建议采用以下状态视图：

| 状态 | 业务档案 | 认证身份 | 是否可登录 | 说明 |
| --- | --- | --- | --- | --- |
| 待开通 | 有效 | 无 | 否 | 已纳入组织，但尚未授予登录能力 |
| 正常 | 有效 | 已绑定 | 是 | 会话有效且用户未被禁用 |
| 禁用 | 有效 | 可有可无 | 否 | 保留历史关系，但拒绝所有新旧会话 |
| 已删除 | 软删除 | 可解绑或保留待清理 | 否 | 退出日常查询，历史证据仍可解释 |

禁用与删除不能混为一谈。禁用是可恢复的业务状态，适合临时停用；删除表示业务档案退出有效集合，需要先处理负责人、部门成员等引用关系。

## 四、身份创建路径

### 4.1 管理员先建档、后开通

管理员先创建业务用户，完成部门、职位、标签和初始角色配置。开通登录时再创建认证身份，并用业务账号绑定已有档案。

方案要求：

- 开通前校验目标用户有效且尚未绑定身份；
- 认证身份的账号信息必须与业务账号一致；
- 绑定完成后再次确认一对一关系；
- 创建成功但绑定失败时删除新身份，恢复为“待开通”；
- 已开通账号不允许只修改业务账号，以免认证标识与业务标识分裂。

### 4.2 用户自助注册

自助注册同时创建认证身份和业务档案。新用户只能获得预先定义且启用的访客角色，不能由客户端指定初始角色、部门负责人或系统状态。

注册流程需要先确认最小权限角色可用，再创建身份并绑定档案。任一步失败时回收新创建的身份或档案，最终只能是“完整注册”或“完全未注册”。

### 4.3 受控初始化

初始管理员账号不应把密码写进初始化数据或数据库变更中。部署完成后，通过受控的一次性流程创建或重置认证身份；该流程默认关闭，仅在明确授权、提供临时密码和指定账号范围时开启。

## 五、会话生命周期

### 5.1 登录

登录分为业务校验和凭据校验：

1. 规范化业务账号。
2. 确认业务用户存在、未删除、未禁用并已开通登录。
3. 由身份服务校验凭据。
4. 确认返回身份确实绑定该业务用户。
5. 汇总最新用户、角色、权限和菜单上下文。
6. 更新最近登录时间并返回会话。

这样可以区分“凭据错误”“账号被禁用”和“尚未开通登录”，也不会只凭身份服务成功就绕过业务状态。

### 5.2 会话恢复与刷新

访问令牌只证明身份服务认可当前会话，不能永久代表业务权限。因此会话恢复、令牌刷新和受保护访问都要重新确认业务用户状态，并获取最新授权上下文。

前端应在令牌临近过期时主动刷新，并把同时发生的刷新请求合并，避免多个刷新请求竞争。业务访问收到未认证结果后最多强制刷新并重试一次；再次失败就清除本地会话，防止无限重试。

### 5.3 会话持久化

“保持登录”只决定会话存入长期存储还是当前浏览器会话存储，不允许保存密码。记住账号也只保存账号文本，不能保存或还原历史密码。

浏览器存储属于体验机制而非安全边界。服务端仍需在每次受保护访问时检查令牌、用户状态和权限。

### 5.4 注销与失效

注销应撤销可继续换取会话的刷新凭据，并始终清理本地状态。即使远端会话已失效或网络失败，浏览器也不能继续保留“看似登录”的状态。

用户被禁用、软删除或解绑身份后，现有访问必须在下一次服务端校验时失效，而不是等到前端主动退出。

## 六、个人资料与密码

个人资料自助修改仅开放不影响身份边界和授权边界的字段，例如姓名、业务邮箱、电话、职位和办公信息。账号、状态、角色、部门负责人关系等高影响字段仍由管理能力控制。

密码只交给身份服务：

- 当前用户可以修改自己的密码；
- 具备专门管理权限的管理员可以为指定用户重置密码；
- 业务数据库、初始化数据、审计记录和日志均不得保存明文密码；
- 如果认证邮箱只是内部标识而不能收信，就不设计虚假的邮件找回流程。

## 七、异常与边界场景

| 场景 | 设计处理 |
| --- | --- |
| 业务档案存在、身份不存在 | 保持待开通，不允许登录 |
| 身份存在、绑定档案失败 | 回收新身份并记录失败原因 |
| 账号已绑定其他身份 | 拒绝覆盖，进入人工核对 |
| 用户被禁用但令牌尚未过期 | 服务端重新校验时立即拒绝 |
| 角色在会话期间被撤销 | 下一次授权计算使用最新角色，不沿用旧结果 |
| 管理员重置密码失败 | 不修改业务档案状态，返回可重试结果 |
| 注销远端失败 | 清理本地会话，并记录远端撤销失败供追踪 |
| 已开通用户要求改账号 | 拒绝单边修改；未来需设计身份与业务账号的联合迁移流程 |

## 八、安全设计

- 身份服务的高权限凭据只存在于服务端。
- 认证请求在生产环境必须使用安全传输。
- 密码、访问令牌、刷新令牌和授权头不进入审计正文。
- 账号存在性、禁用状态和凭据错误的外部提示需权衡用户体验与枚举风险。
- 管理员开通身份和重置密码使用独立权限，不能隐含在普通用户编辑权限中。
- 认证身份创建与业务角色分配相互独立；身份创建不能自动获得高权限角色。

## 九、验收标准

- 可以只创建业务档案而不创建登录身份。
- 自助注册只能获得最小权限角色，客户端无法指定更高权限。
- 正常、未开通、禁用、凭据错误四种情况有明确且稳定的结果。
- 禁用用户和撤权用户的现有会话能及时失效或降权。
- 并发刷新不会产生相互覆盖的会话状态。
- 登录开通的跨系统失败不会留下孤立身份或错误绑定。
- 密码和令牌不会出现在业务数据、审计内容或普通日志中。
- 已绑定身份的业务账号不会被单边修改。
