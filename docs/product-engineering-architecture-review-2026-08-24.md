# 产品与工程架构审查问题及建议

> 审查日期：2026-08-24  
> 审查范围：React 前端、NestJS API、Supabase/PostgreSQL Migration 与 Seed  
> 说明：本文仅记录发现的问题、整改建议及待确认事项。菜单树、菜单名称、层级和排序保持现状。

## 一、结论

未发现可直接确认的 P0，发现 7 项 P1。2026-08-24 已完成第一阶段 P1 的代码修复；新增文件删除状态机 Migration 尚未应用到实际数据库，认证限流为单实例应用兜底，多实例生产仍需共享网关或 Redis 限流。

已完成的 P1：

- 限制角色权限转授范围，并在权限 Dialog 禁用不可委派权限。
- 用户契约改为多角色数组；无分配权限时不加载、不提交角色字段。
- 非 ready 文件禁止预览、下载和新增绑定；预览改用下载权限。
- 文件删除增加可重试状态和数据库原子收尾函数。
- 登录、注册、刷新和当前用户改密增加可配置限流；安全日志只记录哈希标识。

## 三、数据库调整建议

仅列出需要变更的部分：

| 对象 | 建议 | 是否需要 Migration | 数据风险 |
| --- | --- | --- | --- |
| `files` | 扩展删除处理中和失败状态；让状态参与签名访问门禁 | 是 | 上线前需核对数据库记录与 Storage 对象是否一致，并回填异常状态 |
| `file_links` | 增加资源类型/字段注册约束，或对固定业务对象拆分显式关联表 | 视方案而定 | 需先扫描孤儿绑定和未知资源类型 |
| `dashboard_metrics` | 将展示文本拆为结构化数值、单位和格式 | 是 | `$`、`,`、`%` 等历史值需解析；无法解析项保留兼容展示字段 |
| `dashboard_modules` | 增加 `capacity > 0`、`value >= 0`、`value <= capacity` 约束 | 是 | 加约束前需查找并修复异常历史数据 |
| `notifications` | 增加失效时间晚于创建/发布时间的检查约束 | 是 | 风险低，先检查现存异常值 |
| `audit_logs` | 评估移除未使用的 changes GIN，制定归档与保留策略 | 可能 | 删除索引应使用低锁方式；归档周期需满足合规要求 |
| 认证安全事件 | 为登录失败、限流、密码操作建立独立事件表 | 是 | 注意脱敏，不保存密码、令牌和完整认证头 |

`users`、`user_roles`、`role_permissions` 的首要问题是 API 与权限逻辑，不建议在确认多角色业务语义前调整现有表结构。

## 四、页面调整建议

### 用户管理

- 增加账号、部门、角色、登录开通状态筛选。
- 无 `users.assign_roles` 权限时，角色字段不显示、不加载、不提交。
- 多角色使用可搜索多选；资料编辑不得隐式覆盖角色集合。
- 编辑前重新读取详情，并使用乐观锁防止覆盖他人修改。
- 删除前说明 Auth 身份、角色和组织依赖的处理结果。

### 角色管理

- 权限 Dialog 禁止勾选操作者自身没有或不可委派的权限，并说明禁用原因。
- `scope` 若只是描述，应在页面显示为“权限范围说明”，不得让用户误认为它控制数据范围。
- 建议显示成员数和权限数，删除失败时给出具体依赖信息。

### 组织架构

- 增加编码、上级部门筛选，树视图支持名称或编码定位。
- 明确“创建部门 → 调入成员 → 设置负责人”的操作顺序。
- 导入预检与数据库负责人归属规则保持一致。
- 导出使用独立权限并写入审计。

### 菜单管理

- 菜单树、名称、层级和排序保持现状。
- 管理表格建议显示编码、组件类型、可见性和排序值，便于核对实际配置。
- 保留前端父子过滤和数据库防环双重校验。
- 引入真实 URL Router 时继续使用现有菜单 path，不调整信息架构。

### 文件管理

- 增加服务端分页及名称、类型、状态、上传人、日期筛选。
- 概览数字改由服务端聚合，不能只统计当前 100 条。
- 正确显示 ready、quarantined、failed，并按状态控制操作。
- 修复预览/下载权限重叠和隔离文件访问问题。
- 删除改为状态机和统一 Dialog，显示引用影响。

### 审计日志

- 增加时间范围、账号、请求 ID 和资源 ID 筛选。
- 明确标记被截断的证据字段。
- 仅信任可信代理提供的客户端 IP。

### 登录、注册与个人中心

- 增加认证限流和安全事件。
- 提高密码策略，并根据风险决定是否要求近期认证或当前密码。
- 减少 refresh token 暴露在 JavaScript 可读存储中的时间。
- 确认头像公开策略，并加强真实图片校验。

### 通用资源列表

- Enter 提交筛选，筛选后回到第一页。
- 筛选、分页和排序写入 URL，返回页面时恢复。
- 区分请求失败、首次无数据和筛选无结果。
- 导出使用独立权限和服务端实现。

## 五、实施顺序

### 第一阶段：P1

1. 限制角色权限转授范围。

5. 补齐用户软删与 Auth 身份生命周期。

1. 文件分页、筛选和聚合。

3. 筛选 URL 化和错误状态区分。
4. 搜索索引治理。
5. 统一危险操作 Dialog。

### 第四阶段：维护性

1. 引入真实路由，但保持现有菜单树不变。
2. 拆分 `ResourcePage` 的资源特定逻辑。

| 问题 | 建议默认方案 | 不同选择的影响 |
| --- | --- | --- |
| 用户是否允许多角色 | 按现有数据库和设计，继续允许多角色 | 若决定单角色，必须增加数据库唯一约束并迁移现有多角色数据，不能只改 UI |
| Operator 创建用户时的默认角色 | 服务端赋最小 guest，或创建无角色且未开通登录的档案 | guest 使用方便；无角色更安全但需要后续开通步骤 |
| 预览是否等同下载 | 返回原文件即视为下载权限 | 真正只读预览需要生成派生预览件，开发与存储成本更高 |
| 头像是否允许永久公开 | 默认按私有处理，除非产品明确其为公开资料 | 私有头像需签名刷新；公开头像需隐私告知并与私有附件文案区分 |
| 用户软删是否允许恢复 | 支持受审计恢复，并同步 Auth ban/unban | 不恢复则需定义最终清理期限和合规删除策略 |
| `roles.scope` 是否控制数据权限 | 默认仅作为描述字段 | 若需要真实数据范围，必须另建结构化授权策略，不能直接解释自由文本 |
| 部门导入能否自动调整负责人所属部门 | 默认不自动调岗 | 自动调岗会影响原部门负责人和成员关系，需要更复杂的事务与冲突提示 |
| 审计写入失败是否阻断业务 | 普通后台保持业务成功，同时告警审计缺口 | 合规场景需要事务或可靠消息，会增加延迟和系统耦合 |
