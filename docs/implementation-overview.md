# 后台管理系统设计方案总览

## 文档定位

本文描述后台管理系统“应该如何设计和落地”，用于统一产品、前端、后端、数据库和测试对方案的理解。它只保留总体目标、系统边界、核心决策和实施顺序；领域细节拆分到专题方案中。

本文不描述具体代码结构、类或函数，也不绑定某一种接口写法。后续实现可以调整技术细节，但不得绕过本文定义的安全边界和数据不变量。

## 一、设计目标

系统需要同时满足以下目标：

1. 身份认证与业务用户档案相互独立，允许“先建档、后开通登录”。
2. 使用一套可解释、可审计的 RBAC 模型覆盖页面、按钮和业务操作。
3. 菜单由后台配置驱动，但菜单可见性不替代业务权限判断。
4. 用户、角色、权限、部门等核心数据在并发和失败场景下保持一致。
5. 审计、文件、通知和仪表盘作为独立能力接入，不污染权限核心模型。
6. 浏览器只接触必要的公开信息，敏感凭据和最终授权判断均留在服务端。
7. 方案支持逐步扩展到更多资源类型，而不需要复制新的认证或权限体系。

## 二、总体架构

系统划分为四个责任层：

| 层级 | 主要责任 | 设计边界 |
| --- | --- | --- |
| 展示层 | 页面交互、导航渲染、按钮显隐、会话体验 | 只做体验性权限提示，不作最终授权裁决 |
| 应用层 | 身份校验、权限判断、业务规则、模块编排 | 所有业务访问的唯一入口 |
| 数据层 | 业务数据、关系约束、原子操作、审计证据 | 负责不可被应用绕过的数据不变量 |
| 身份与对象存储层 | 登录凭据、会话原语、私有文件对象 | 不承载业务角色，也不直接暴露给浏览器操作 |

总体原则是：展示层可以隐藏无权操作，应用层必须拒绝无权操作，数据层必须阻止不一致操作。三层职责互补，任何一层都不能单独替代另外两层。

## 三、核心领域划分

### 3.1 身份与用户

认证身份只回答“这个人是否能证明自己是谁”，业务用户档案回答“这个人在系统中是谁、处于什么状态、属于什么组织”。两者通过唯一关联连接，但生命周期独立。

详细方案见 [身份、用户与会话设计](design/identity-user-session.md)。

### 3.2 角色、权限与菜单

角色是权限集合，用户可以拥有多个角色，最终权限取启用角色的授权并集。菜单是导航投影，只根据权限决定是否展示，不参与接口授权本身。

详细方案见 [RBAC 与菜单设计](design/rbac-menu.md)。

### 3.3 企业后台能力

部门、仪表盘、通知、审计和文件各自形成独立业务能力，共享统一身份、权限、软删除和审计规则，不再建立各自的用户或角色体系。

详细方案见 [业务能力设计](design/business-capabilities.md)。

### 3.4 一致性与安全

跨记录替换、批量导入、身份开通和文件上传都可能发生部分失败。方案需要提前定义事务边界、补偿策略、安全边界和可观测信息。

详细方案见 [数据一致性、安全与演进设计](design/consistency-security-evolution.md)。

### 3.5 模块数据库与接口

领域方案定义“为什么这样设计”，模块详细设计进一步定义“保存什么数据、提供什么接口、遵守什么约束”。统一约定与完整导航见 [模块数据库与接口设计](design/modules/README.md)。

## 四、核心对象与关系

| 对象 | 设计含义 | 主要关系 |
| --- | --- | --- |
| 认证身份 | 登录凭据与会话主体 | 最多关联一个业务用户 |
| 业务用户 | 人员档案与业务状态 | 属于部门，可拥有多个角色 |
| 角色 | 一组可复用授权 | 可分配给多个用户，可包含多个权限 |
| 权限 | 对某类资源执行某种动作的能力 | 可被多个角色授予，也可控制菜单显示 |
| 菜单 | 导航树中的目录或页面入口 | 可有父菜单，可绑定一个显示权限 |
| 部门 | 组织树节点 | 可有父部门、负责人和成员 |
| 通知 | 面向用户的时效信息 | 与用户形成独立已读关系 |
| 审计记录 | 对业务操作的不可变证据 | 保存操作者快照和操作上下文 |
| 文件 | 私有对象的业务元数据 | 可绑定到一个或多个业务资源字段 |

这些对象使用稳定标识建立关系，名称仅用于展示。名称变化不应破坏授权、树结构或业务绑定。

## 五、关键业务流程

### 5.1 新用户进入系统

新用户有两条路径：先创建业务档案再开通登录，或通过注册同时创建认证身份和业务档案。无论哪条路径，首次获得的角色都必须是最小权限角色；身份创建或档案绑定失败时不能留下半开通状态。

### 5.2 受保护操作

一次受保护操作需要依次确认：会话有效、业务用户有效、动作权限满足、目标资源允许操作、数据约束满足。前一步失败就停止后续处理，并返回稳定、可解释的失败原因。

### 5.3 角色分配

角色分配不仅检查“是否拥有分配角色的权限”，还要检查目标角色是否受保护，以及该角色包含的权限是否超出操作者自身权限，避免通过转授形成权限提升。

### 5.4 导航生成

系统先根据用户权限选择可访问页面，再补齐这些页面的父级目录，形成完整导航树。用户看不到的菜单不代表业务访问可以放松校验；用户看到菜单也不代表可以执行该页面上的全部动作。

### 5.5 批量或跨系统操作

角色权限替换、用户角色替换和部门导入必须整体成功或整体失败。涉及身份系统或对象存储的操作无法与业务数据库共用事务时，采用明确的执行顺序和补偿动作，避免形成不可解释的中间状态。

## 六、跨领域设计原则

### 最小权限

新身份默认获得最低可用权限；敏感操作拆分为独立权限；服务端凭据只用于服务端；私有文件不提供永久公开地址。

### 权限可解释

任意授权结果都能通过“用户持有哪些启用角色、角色包含哪些启用权限”解释，不引入隐式优先级、显式拒绝或菜单反向授权。

### 约束前置

业务层在写入前给出清晰校验结果，数据层再用唯一性、引用、树环和保护规则兜底。对核心不变量不能只依赖页面限制。

### 失败可恢复

每个跨边界流程都要定义主操作、补偿动作、最终状态和人工修复入口。无法自动恢复的情况必须可通过审计上下文定位。

### 变更可演进

权限编码、角色编码、菜单编码和部门编码作为稳定业务标识。展示名称、文案和排序可以变化，稳定标识不随界面调整而变化。

## 七、实施阶段

### 阶段一：建立身份与数据边界

完成业务用户与认证身份分离、会话生命周期、服务端统一访问和基础数据约束。此阶段先保证“身份可信、数据入口唯一”。

### 阶段二：建立 RBAC 闭环

完成角色、权限、用户授权、动作校验、越权保护与菜单投影。此阶段需要同时覆盖页面可见性和服务端拒绝能力。

### 阶段三：接入业务模块

按统一资源规范接入部门、仪表盘和通知，再接入审计与文件。每个模块必须声明自己的数据所有权、权限集合和失败边界。

### 阶段四：补齐可靠性与验收

完成原子替换、批量导入、补偿处理、敏感信息脱敏、操作追踪和异常回归。只有正常路径与失败路径都可验证，方案才算闭环。

## 八、非目标与后续演进

当前方案不引入多租户、数据行级范围授权、显式拒绝、角色继承和审批流。它们都可能改变权限语义，不能以增加字段的方式临时叠加。

如果未来需要多租户，应把租户维度加入用户授权和业务数据边界；如果需要数据范围权限，应在动作权限之外增加独立的范围策略；如果需要审批，应把待审批状态建模为业务流程，而不是把审批结果塞进角色或菜单。

## 九、总体验收标准

- 未登录、账号禁用、无动作权限和目标资源受保护四类失败能够被明确区分。
- 用户的最终权限可以从角色与权限关系完整解释。
- 隐藏菜单不能绕过服务端授权，直接访问无权资源仍被拒绝。
- 角色或权限变化能及时影响后续访问，不依赖用户重新注册。
- 关系替换和批量导入不会出现部分生效。
- 身份开通和文件操作失败后，不遗留无法解释的孤立记录或公开对象。
- 审计信息能够回答谁、何时、对什么执行了什么，以及结果如何，同时不记录密码和令牌。
- 系统角色、系统权限和关键引用关系不能被普通管理操作破坏。
